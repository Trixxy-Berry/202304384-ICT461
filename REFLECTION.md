Building this form showed me why semantic HTML actually matters, not just visual styling. Using '<label 'for="...">' linked to each input's id meant clicking the label focused the right field, and it meant the field would be properly announced to a screen reader. Using a real '<button 'type="submit">' instead of a styled '<div.>' gave me keyboard support for free — tabbing to it and pressing Enter just worked, with no extra JavaScript needed for that. Wrapping the whole form in '<'main>' also gave the page one clear block of actual content, separate from anything decorative.
DevTools was more useful than I expected. The Elements panel let me check that my HTML structure actually matched what I intended — at one point it helped me catch that an element wasn't nested where I thought it was. The Network panel showed index.html and styles.css loading with real status codes and timing, which made performance feel measurable instead of just a concept from a slide.
The biggest lesson was about validation. My JavaScript checks each field on blur or change and shows an error message, which helps a normal user catch typos before submitting. But it doesn't actually stop anyone from bypassing it — someone could open the browser console, disable the script, or send a request straight to a server without ever touching my form at all. So client-side validation is really about user experience, not security. The actual rules — checking a student ID is real, a course isn't full, the data isn't malicious — have to be enforced server-side, because that's the only code a user genuinely cannot edit or skip.
Committing in small stages, one meaningful change per commit, also showed me something I hadn't thought about before: a Git history can document the actual process of building something, including the mistakes along the way, not just the final polished result.
